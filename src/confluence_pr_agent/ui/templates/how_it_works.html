This is the exact sequence a real page change goes through -- every run on the Pipeline Runs page is a snapshot of this same diagram, live or finished.

1 · Confluence page changes

A Confluence spec page is edited and saved. Confluence sends a webhook (or, for a demo, Simulate Webhook triggers the same code path manually). The agent fetches the page's current content and diffs it against the last version it successfully processed -- computed as a unified diff of the page's plain-text content, not raw HTML, so formatting-only edits don't trigger a false change.

If Confluence label filtering is configured, a page without at least one allowed label is ignored here before any repo work happens. If the version bumped but the content is unchanged (e.g. a metadata-only edit), the run also stops here.

2 · Clone the target repo

The pipeline clones {{ settings.target_repo }} at its base branch ({{ settings.target_repo_base_branch }}) into a fresh working directory and creates a new branch for this change -- one clone per run, so nothing from a previous or concurrent run leaks in.

3 · An AI agent implements the change

A pluggable coding agent reads the repo, understands its conventions, and implements the spec change directly -- writing or updating tests as part of the same change, not as an afterthought. This run is currently configured to use {{ settings.change_agent_engine }}, but the choice (Claude Code, Cursor, GitHub Copilot, Codex, Gemini, Antigravity) is a config switch, not a code change -- see Configuration.

If the agent fails outright, or makes no file changes at all, the run stops here with nothing pushed anywhere.

4 · Gate #1 -- the repo's own tests

The target repo's own test command ({{ settings.target_repo_test_command }}) runs against the change, unmodified. This is a mechanical check: does the code still work, by the repo's own definition of "works"? A failure blocks the PR entirely -- the run ends as Tests Failed and the Confluence page version is deliberately not marked as processed, so the exact same diff is retried on the next webhook rather than silently dropped.

5 · Gate #2 -- LLM Judge review

Passing tests doesn't prove the spec was actually implemented -- a green suite can't tell the difference between "correct" and "coincidentally didn't break anything." This gate is a semantic check: an independent model ({% if settings.judge_enabled %}currently {{ settings.judge_provider }}{% else %}currently disabled{% endif %}) is shown the spec change, the agent's own summary, and the actual code diff, and has to decide -- does this diff really do what the spec asked, scoped to just that change, with tests that exercise the new behavior? It can still say no even after tests pass.

A rejection ends the run as Judge Rejected with its written reasoning and specific concerns attached to the run -- same not-marked-as-processed retry behavior as a test failure. If the judge's own API call isn't configured or fails, this step fails open (skips the review) rather than blocking a change that otherwise passed its own tests -- a second opinion that's unavailable shouldn't cost a good PR.

Independent of the change engine on purpose, in both provider and model, so it isn't the same model grading its own work. Toggle it, and switch between Anthropic and OpenAI, from Configuration.

6 · Pull request opens

Once both gates pass, the change is committed, pushed to its own branch, and a PR opens against {{ settings.target_repo_base_branch }} -- titled after the spec page, with the agent's summary and the list of changed files in the description, and a link back to the source Confluence page. Only now does the pipeline record this page version as processed.

7 · Team notified

A summary email goes out to the configured recipients with the spec diff, the change summary, and a link to the PR. This step is best-effort and deliberately isolated from everything before it -- an unconfigured or failing email step never turns an already-opened PR into a reported failure; it just shows up as "not sent" on the run.
